# HTTP の JSON を json v2 へ替える手引き

goutil の `webframework` を使うプロダクトが、HTTP の JSON を `encoding/json/v2` へ替えるときの進め方です。替えた後に「意図しない変化が無い」と言える状態を、本番を替える前に作ることを目的にしています。

要点は 3 つです。

- PR を 3 つに分けます。無関係な整理、v1 のままで差を出す試験、本番の切り替えの順です。切り替えの PR は設定の 1 行と、その結果の直しだけにします。
- 本番を替える前に、同じ要求を v1 と v2 の app へ送って応答を比べる試験を作ります。差は 1 件ずつ「採る」か「直す」かを決め、一覧として残します。
- 切り替えの PR では、実バイナリの結合テスト、画面の E2E、外のクライアント(端末の agent など)の E2E を v2 で通してから merge します。

## 進め方

1. **無関係な整理を先に出す。** lint の自動修正(modernize など)のような大きな機械的な差分は、JSON の PR と混ぜません。差の試験の結果を読むときに、どの変化が JSON から来たのかが分からなくなります。
2. **差を出す試験の PR(本番は v1 のまま)。** 次を入れます。この PR では本番の挙動を変えません。
   - 本番の app と試験の app が共に読む、JSON のモードの定数(`gw_web.JSONV1`)。
   - 試験の app も同じモードで作る関数。
   - v1 と v2 の差の試験と、差の一覧。
   - v1 でも v2 でも意味が同じになる直し(`omitzero` など)。
3. **本番の切り替えの PR。** モードの定数を `gw_web.JSONV2` にし、関門(後述)を通します。差の試験などの移行のための道具は、この PR で消します。

## goutil での設定

`AppSettings.JSON` を `gw_web.JSONV2` にすると、Fiber の `JSONEncoder` と `JSONDecoder` が v2(`json.DefaultOptionsV2()`)になります。ゼロ値の `gw_web.JSONV1` なら v1 のままです。使い方は [README](../README.md)「JSON を json v2 で読み書きする」にあります。

- **細かく決める時だけ `AppSettings.JSONOptions` を使います。** 1 つずつ外していく形(`DefaultOptionsV1()` に v2 の挙動を足す)もできます。ただし、どこまで替えたかを後で追いにくくなるので、決められるなら `JSON: gw_web.JSONV2` で一度に揃える方が簡単です。`JSONV2` と `JSONOptions` を同時に指定すると、app を作る時に panic します。
- **map の順番は固定しない方を勧めます。** v2 の既定(`Deterministic(false)`)では、map の順番は保証されません。固定すると、画面や試験が順番に頼っていても気づけません。固定しなければ、順番に頼る所が落ちやすくなります(毎回変わるとは限らないので、1 回通っただけでは頼っていない証拠になりません)。順番に意味がある物は配列で返します。
- 固定するときは、`json.Deterministic(true)` を `DefaultOptionsV2()` より後ろに置きます(後ろのオプションが勝ちます)。
- **オプションの一覧は、読み込みと書き出しの両方に渡ります。** 片方にだけ効く物(`Deterministic` は書き出しだけ、`RejectUnknownMembers` は読み込みだけ)と、両方に効く物があります。例えば `StringifyNumbers` を足すと、要求の数値を文字列で受けるだけでなく、応答の数値も文字列になります。

## v2 で変わること

Go 1.27 で確かめた違いです。左の列の変化ごとに、切り替えの前にやる事を決めます。誤りになったときの status(400 か 500 か)は、ハンドラーの誤りの扱いで決まります。

| 変化 | 起きうる害 | 切り替えの前にやる事 |
|---|---|---|
| struct の項目へのキーの照合が、大文字・小文字を区別する。照合の相手は、タグがあればタグの名前、無ければ Go の項目名 | 送るキーと受けの名前の綴りが一字でも違うと、値が黙って捨てられる。必須の項目なら誤りになる。map のキーには関係しない | 外のクライアントが送るキーを、受けの型の有効な名前と突き合わせる(後述の「外のクライアントの本文」) |
| 同じキーが 2 回ある本文は誤り | 今は通っている本文が 400 になる | 差の一覧に載せて採る(どちらの値を使うか曖昧な本文を断る方が安全) |
| nil の slice は `[]`、nil の map は `{}`、nil の `[]byte` は `""` で書き出す | 画面の `v-if="x"` のように真偽で見ている所が、`[]`・`{}` を「ある」とみなして表示が変わる | 画面で、該当する項目の真偽の判定を探して直す。差の試験で、どの応答のどの項目かを出す |
| `omitempty` は「書き出した JSON が空(`null`・`""`・`[]`・`{}`)なら省く」になる。数値・真偽値のゼロは書き出し、空文字を指すポインターや `{}` になる struct は省く | 今は省いている `0` や `false` が応答に出る。逆に、今は出している `""` や `{}` が欠落になる(欠落と空の値を区別する PATCH や画面で効く) | 数値・真偽値と、組み込みの型へのポインター(`*string` など)の `omitempty` を `omitzero` に替える(v1 でも意味は同じなので、差の試験の PR に入れられる)。`IsZero` を持つ型へのポインター(`*time.Time` など)は替えない(`omitzero` は指す先の `IsZero` を呼び、ゼロの時刻を省くようになる。`omitempty` のままなら v1 と v2 で同じ)。struct の `omitempty` は v1 では効いていないので、外すか、省いてよいかを決める |
| `time.Duration` は、書き出しにも読み込みにも既定の表現が無く、誤りになる | 応答や読み込みが誤りになる | JSON に出す型に `time.Duration` が無いかを探す。v1 の表現(ナノ秒の数値)を保つなら、`DefaultOptionsV2()` の後ろに `encoding/json` の `FormatDurationAsNano(true)` を足す。秒の数値へ替えると意味が変わる |
| 不正な UTF-8 を含む文字列は、読み込みでも書き出しでも誤り | 今は通っている本文が誤りになる。DB や外から届いたデータを応答に詰めている所では、応答が誤りになる | 読み込みは多くの場合採ってよい。書き出しは、外から届く生の文字列を応答に詰めている所を確かめる |
| 固定長の配列は、要素の数が違うと誤り。`[N]byte` は数値の配列ではなく Base64 の文字列になる | 今は通っている本文が誤りになる。`[N]byte` の応答の形が変わる | 型の情報から該当する項目を探す |
| 初期値を入れた値に `null` を読み込むと、v2 ではゼロになる(v1 は宛先の型による。ポインター・map・slice・interface は nil になり、`int` などはそのまま残る) | 既定値を入れてから読み込む作りで、`null` が届くと既定値が消える | 既定値を入れてから読み込んでいる所を探す |
| HTML の文字(`<`、`>`、`&`)をエスケープしない | 応答を HTML に埋め込んでいる所があれば危ない | JSON の応答を HTML に埋め込んでいないかを確かめる |
| 誤りの文が変わり、入力の値の一部や Go の型の名前を含むことがある | `err.Error()` をそのまま応答に載せていると、送られた値が応答と利用側のログに残る | 読み込みの誤りは、値を含まない固定の文で返す(後述) |
| 未知のキーは、v1 と同じく既定では無視する | 変化は無い | 未知のキーを拒む読み込みは、自分で `RejectUnknownMembers(true)` を足す |

## 設定が届かない所を数える

Fiber の `JSONEncoder` と `JSONDecoder` を通る経路だけが替わります(README に一覧があります)。次は替わらないので、1 つずつ「揃えるか、v1 のまま残すか」を決めます。数えるときは、関数の名前で grep し、呼ぶ所の数まで出します。名前から用途を推測して範囲を狭めないでください。

- **自前の読み込み。** `json.Unmarshal` や、`json.NewDecoder` と `DisallowUnknownFields` で本文を読む関数は、v1 のままです。HTTP の本文を読むなら、`ctx.DecodeJSON`(app の設定で読む)か `ctx.DecodeJSONStrict`(知らないキーと後ろに続く値を断る)に替えます。どちらも要求を受けた app の設定で読むので、1 つのプロセスに v1 と v2 の app があっても混ざりません。
- **HTTP 以外の入力。** AI のツールの引数のように、同じ関数で HTTP 以外の JSON も読んでいるときは、その呼び出しを HTTP の設定から外します。HTTP の切り替えで、別の契約まで変わらないようにするためです。
- **直接 `encoding/json` を呼ぶ所。** ETag の元にする本文、ログの生の JSON、WebSocket と NDJSON の自前の読み書き、誤りの本文の書き直しなどです。
- **SharedStorage に保存済みのデータ。** 替えた後に読み戻せるかを確かめます。

## 試験の作り方

### モードを 1 か所で決める

本番の app と試験の app が同じモードを使うように、モードの定数を 1 つ置き、両方の app をそれで作ります。試験の app も、直接 goutil から作らずに、その定数を渡す関数から作ります。そうしないと、本番の定数を `JSONV2` に替えても、試験の app だけ v1 のまま残ります。

```go
// 本番と試験の app が共に読む。v2 へ替える PR で、ここを gw_web.JSONV2 にする
const JSONMode = gw_web.JSONV1

gw_web.NewAppWithSettings(errorHandler, &gw_web.AppSettings{JSON: JSONMode})
```

- goutil の app を直接作る呼び出しは、lint で止めます。golangci-lint の forbidigo で `analyze-types: true` にし、`pkg` に goutil の import path を書きます。`pattern` は import path ではなく、呼び出しに使う**パッケージ名**(例: `^gw_web\.NewApp.*$`)で書きます。本番の app と試験の app を作る 2 つのファイルだけ、除外に入れます。
- 試験のための環境変数は作りません。試験の全体を v2 で流したい時は、手元で定数を `JSONV2` に替えて流します。差の試験は、後述の `jsontest.Build` でモードを指定して app を作ります。

### v2 で試験の全体を流す

- 手元で定数を `JSONV2` に替えて `go test ./...` を流し、既存の試験をすべて v2 で流します。応答を文字列のまま比べている試験は、map の順番で落ちます。読み込んでから比べる形に直します(この直しは v1 のままでも正しいので、差の試験の PR に入れられます)。

### v1 と v2 の差の試験

同じ要求を v1 の app と v2 の app へ送り、応答の差を一覧(golden のファイル)と比べます。app は、本番と同じ組み立ての関数を `jsontest.Build` の中で呼んで作ります。

```go
v1 := jsontest.Build(gw_web.JSONV1, application.BuildApp)
v2 := jsontest.Build(gw_web.JSONV2, application.BuildApp)
```

`jsontest.Build` は、その間に goutil の `NewApp*` で作った app を、`AppSettings` に関わらず指定のモードにします。上書きはプロセス全体で 1 つなので、並行に走る試験では使いません。

- **上書きが届いているかを確かめる試験**を置きます。組み立ての関数が app を作り置きしていると、`jsontest.Build` の上書きが届かず、両方とも v1 で比べてしまいます。v1 と v2 で結果が違う本文(大文字のキーなど)を、それぞれの app の本物のルートへ送り、モードどおりの結果になることを確かめます。一覧は「v2 へ替えると変わる契約」そのものになるので、1 行ずつ採るか直すかを決めます。

比べ方の約束です。

- 無視してよいのはキーの順番だけです。`null`・`[]`・`{}`・欠落はすべて区別します。数値は `UseNumber` で読み、桁まで比べます。数値と文字列も区別します。
- status と Content-Type は常に比べます。本文が毎回変わる応答でも、status の差は隠しません。
- 毎回変わる値(時刻・生成した ID・token)の扱いは、範囲を狭く取ります。
  - 読む API では、v1 を 2 回流して違った所だけを「比べない」とし、一覧に `(not compared)` として出します。黙って捨てません。
  - ID・時刻らしい文字列を同じとみなすのは、書く API の応答だけにします。
- 一覧を安定させるため、配列の添字は `[*]` に、パスの中の UUID は `<id>` に置き換えます。
- JSON の後ろに余計なデータがあれば、差として扱います。

網羅の約束です。

- GET のルートは、ルーターから全部を取り出し、試しの ID を入れて送ります。ただし試しの ID が合わず、エラーの応答しか比べていないルートが多く出ます。**200 を一度も返さないルートは `(no 200)` として一覧に出し**、網羅を多く見せないようにします。
- 主な画面の読み取りは、正しい組の引数で別に送り、v1 で 200 になることを確かめます。
- 書く API では、画面と同じ形の本文に加えて、壊れた本文・重複したキー・大文字のキー・型の違う値を送ります。両方のモードで同じ失敗になる本文も 1 つは入れ、「差が無い」だけでなく、期待する status・誤りの code・文まで確かめます(両方が同じように壊れても、差は出ないため)。
- 書く API は、モードごとに同じ初期状態から作った別の fixture(別の DB)へ送り、応答と保存した値を比べます。1 つの DB に順に書くと、ユニーク制約・前提の確認・件数の上限などで、先のモードの書き込みが後のモードの結果を変えます。
- 試験の準備のデータは合成で作ります。実データを含む seed は使いません。そのため行の無い表の項目(要素の中の nil の slice など)の差は出ません。何が見えないかを PR に書き、切り替えの PR の E2E で補います。

モードの持ち方です。

- **モードは app ごとに固定します。** goutil は app を作る時にモードを決め、`DecodeJSON`・`DecodeJSONStrict` も要求を受けた app のモードで読みます。呼ばれた時にプロセス全体の設定を読む自前の読み込みが残っていると、1 つのプロセスで 2 つのモードを比べたときに、v1 の app への要求でも v2 で読んでしまいます。前の節の「自前の読み込み」を先に替えます。
  - それが重いなら、モードごとに別のプロセス(別の `go test` の実行)で応答を集め、後で比べます。
- app を作る関数が DB の接続を開き直すなら、両方の接続を閉じます。

### 外のクライアントの本文

端末の agent(Rust の serde)のような外のクライアントは、v2 の大文字・小文字の区別で最も壊れやすい相手です。

- クライアントの型から、送る本文の形をそのまま写します(serde の `rename_all` を当てた後のキー名)。
- その本文を、本番と同じ設定の試験の app の `BodyParser`(と自前の厳しい読み込み)へ通し、受けの型へ読み込みます。読み込んだ値を v1 で書き出し直し、送ったキーと値がすべて残っているかを比べます。数値は桁まで、型も含めて比べます。`None` が `null` で届く場合も入れます。
- クライアントが送るが、サーバーが保存しないキーは、その試しの中で名前を挙げて除きます。黙って捨てません。
- 中で名前の無い struct として書いている受けの型は、試験から参照できるように名前を付けます。
- 生の本文を受ける経路(ログの一括送信など)は対象の外です。その旨を書きます。

### 静的な棚卸し

型の情報(`go/packages`)を使い、上の表の変化に当たる項目を全部集めます。

- `BodyParser` と `BindJSON` に渡す型で、json タグの無い export された項目。これは調べる候補の一覧で、合否ではありません。タグが無くても、送るキーが Go の項目名と同じなら値は失われません。タグがあっても、送る側の綴りが違えば失われます。合否は、送るキーと受けの有効な名前の突き合わせ(前の節)で決めます。
- `omitempty` の付いたポインター・struct・配列の項目、`[N]byte` の項目、JSON に出す `time.Duration` の項目。応答の型は呼ぶ所から集めにくいので、モジュールの中の struct すべてを対象にします。

## 読み込みの誤りの文

v2 の誤りの文は、入力の短い文字列や数値、Go の型の名前、入力から作ったパスを含むことがあります。`err.Error()` をそのまま応答の message に載せると、送られた値(秘密の値の経路なら秘密そのもの)が応答と、それを拾う利用側のログに残ります。

- status・誤りの code・どこの誤りか(`body` など)は保ち、message は値を含まない固定の文にします。例えば、壊れた JSON、未知のキー、重複したキー、型の違う値の 4 つに分けます。
- 同じ入力なら v1 と v2 で同じ文になるように作ると、差の試験で誤りの応答も比べられます。
- `BodyParser` の誤りを `err.Error()` のまま載せている所も、切り替えの PR までに同じ扱いにします。

## 本番を替える PR の関門

本番の設定を v2 にした状態で、次をすべて通してから merge します。

- **実バイナリの結合テスト。** `jsontest.Build` は試験のバイナリの中でしか効かないので、ビルドしたバイナリを叩く結合テストは、本番の定数を替えた時にだけ v2 で流れます。
- **画面の E2E の全件。** 画面が送るキーの大文字・小文字と、`[]`・`{}` になった項目の表示を見ます。
- **外のクライアントの E2E。** 配布済みの古い版のクライアントが残るなら、その版でも確かめます。

同じ PR で、次も行います。

- 差の試験・差の一覧と、`jsontest.Build` を使う所を消す(残すと、API を足すたびに一覧の書き直しが要るだけになる)。
- 差の一覧で「直す」と決めた画面の条件を直す。

残す物は、モードの定数、試験の app を作る関数、lint の規則、外のクライアントの本文の試験です。

## lint の道具の注意

- golangci-lint v1.64.8 は、Go 1.27 のコードの解析で panic することを確かめました。v2 系を使い、設定も v2 の形式に書き直します。
- modernize の `omitzero` の解析は、struct の項目の `omitempty`(v1 では効いていない)を `omitzero` に自動で替えます。今は出している空の struct を省くようになり、出力が変わるので、外しておきます。`omitzero` への置き換えは、上の表で v1 と意味が同じと確かめた項目(数値・真偽値、組み込みの型へのポインター)だけ、型の情報から集めて行います。
